# QueryLens local AI model card

## Components and intended use

QueryLens has two distinct learned components. The supervised intent classifier
is trained inside this project from a small labeled English question corpus.
The Qwen language model uses pretrained public weights for local SQL generation.
It was not pretrained or fine-tuned by this project.

The target is an English, synthetic commerce analytics demonstration using two
modeled tables. Neither model is suitable for unsupervised financial decisions,
arbitrary databases, or claims of general business-question accuracy.

## Supervised NLP classifier

- Features: word TF-IDF unigrams/bigrams and character TF-IDF 3–5 grams.
- Estimator: logistic regression with C=6 and seed 42.
- Calibration: sigmoid calibration over three stratified folds. Each fold fits
  the entire text-feature/classifier pipeline, keeping held-out fold documents
  out of that fold's vocabulary and IDF fit.
- Classes: nine unfiltered report intents, each mapped to approved SQL.
- Data: 108 train, 27 dev, and 36 test questions, plus 8 dev and 12 test
  unsupported questions. Text is curated/synthetic and AI-assisted, not user traffic.
- Thresholds: maximum-probability and top-two-margin thresholds selected using
  dev data. Selection seeks high selective precision and rejection of dev OOD
  questions. Test labels are not used for fitting or threshold selection.
- Scope controls catch common explicit filters, forecasts, unavailable fields,
  and unsupported top-N variants. They do not guarantee that every unsupported
  request is rejected; the execution benchmark exposes incorrect accepted cases.

The data splits are explicit in `querylens/ai/data/intents.json`; tests reject
normalized duplicates across splits. They are developer-authored held-out splits,
not a blind external benchmark. Shared domain wording can make these results
more favorable than performance on real user language.

Reports include full-set accuracy/macro F1, a confusion matrix, accepted
coverage, accuracy on accepted predictions, and OOD rejection. The probability
is a calibrated classifier output, not a guarantee of answer correctness.

The serialized joblib model is generated by the application, protected by a
recorded checksum and training-data/library-version checks, and stored in an
ignored local folder. Only load model artifacts you generated and trust;
joblib is not an untrusted-file format.

## Local language-model inference

- Weights: Qwen/Qwen2.5-Coder-1.5B-Instruct-GGUF, Q4_K_M.
- Source: https://huggingface.co/Qwen/Qwen2.5-Coder-1.5B-Instruct-GGUF
- Runtime: llama-cpp-python / llama.cpp, CPU-local, up to 8 threads.
- Context: 4,096 tokens; generation limit: 384 tokens; temperature 0; seed 42.
- Output: grammar-constrained JSON with SQL and a short explanation.
- Provenance: `.querylens/models/model-manifest.json` records the pinned upstream
  revision, published SHA-256 checksum, size, filename, and license.
- Setup downloads data; inference does not call any hosted provider.

This is quantized inference, not quantization research or language-model training.
The explanation can be inaccurate even when SQL is valid. Inspect the SQL and
business assumptions. CPU latency depends on hardware and prompt/output length.

## Retrieval

The retriever fits word TF-IDF unigrams/bigrams and uses cosine similarity to
rank business rules and SQL examples. It always includes the small schema.
Examples come only from the classifier training questions; dev/test questions
and SQL benchmark prompts are not indexed. This is sparse lexical retrieval,
not a pretrained neural embedding model or a vector database.

## Generation evaluation

The execution benchmark contains twelve curated answerable questions and three
unsupported/write requests in `querylens/ai/data/sql_benchmark.json`. Some cases
require filters and top-N values outside the trained classifier's scope.

Four variants are compared: exact example lookup, trained intent routing,
local generation without retrieved context, and local generation with retrieved
context. Only the retrieval setting changes between the two LLM variants;
schema, model, decoding parameters, and core instructions are shared. All
variants face the same questions. This comparison intentionally exposes the
limited scope of the template-based baselines.

Correctness compares generated-query result values with reference-query results
on the same synthetic warehouse. Aliases are ignored; requested row ordering,
row/column counts, values, and numerical tolerances are checked. SQL validity
alone is not answer correctness. Automatic repair is disabled in the ablation
run, and unsupported-question refusals are reported separately. The report's
`refusals` field records pipeline rejection, including SQL-validation failures;
it is not a separate measurement of semantic refusal accuracy by the model.

Reports retain successes, failures, generated SQL, model traces, mean latency,
case counts, and Wilson confidence intervals. The small sample size and single
synthetic warehouse limit what these scores mean; they are not production or
cross-database performance estimates. Repeated model changes after looking at
this test set require a fresh untouched test set for a new unbiased claim.

## Reproduce

```sh
python -m querylens --train-ml
python -m querylens --ai-eval --skip-llm
python -m querylens --ai-eval
```
